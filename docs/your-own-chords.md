# Your own chords and fingerings

A record of the design discussion held 2026-11-01. Proposed, not decided and not built. Nothing in
the code has changed for it yet.

## What Joel asked for

- A way to add fingerings to chords in the chord library, above all the ones that have none.
- A way to add new chords. His example: define Gsus4add6 and give its fingering.
- Notes are given by string and fret, as now, and fingers as 1 index, 2 middle, 3 ring, 4 little.
- Suggestions for the UI, and whether to send the additions to chords-db.
- Then: whether a chord progression saved as .atex can carry chords that are only in the sender's
  library, so that unstrung on another machine says which chords are missing and offers to add
  them.

## The library as it stands

- `src/assets/chords/chord-library.json` is generated by `scripts/build-chord-library.mjs`
  (`npm run build:chords`) from `@tombatossals/chords-db` 0.5.1. It is never edited by hand.
  Since 2026-11-02 the build reads `scripts/chord-library/voicings.json` instead, a copy of what it
  took from chords-db, which is no longer a dependency. See `chord-library-maintenance.md`.
- 564 chords, 38 of them with notes but no fingering (`confidence: "unfingered"`, empty
  `voicings`), such as Cadd11.
- A voicing is six `strings` entries, string 6 first, each `{ string, play, fret, finger }`, with
  `play` one of `fretted`, `open`, `muted`, `barre: true` on strings held by a barre, and a
  `barres` list. Fingers are already numbered 1 to 4, index to little, as Joel asked.
- Chords are matched everywhere by root and suffix: `chordIndex` in `src/shared/songScore.mjs`
  maps display names to library entries, and `progressionFromSong` refuses a chord not in the
  library.
- The suffix must be one `CHORD_FORMULAS` in `src/shared/musicTheory.mjs` knows. There is no
  `sus4add6`, and no `6sus4`.

## Proposed: your chords kept apart from the generated library

- Kept like your own strumming patterns: with the settings (the settings file on the desktop,
  local storage in the web version), with Export My Chords and Import Chords to a file. That
  already works on both, including iOS, where nothing can be saved to a folder.
- Merged into the library when unstrung loads it, so search, the progression editor, chord
  practice, playback and the song's Chord Symbols all see them without knowing where they came
  from.
- The built-in fingerings cannot be changed, for the same reason as built-in strumming patterns:
  a name and a shape always mean the same thing. To change one, copy it to your own and edit the
  copy.
- Your fingerings are marked "yours" and come first for their chord, so they start checked in the
  chord library and chord practice uses them.

### What one of yours holds

- The chord's name, root and suffix.
- For each string, 6 to 1: not played, open, or a fret from 1 to 15.
- For each fretted string, a finger, 1 to 4.
- No barre field. Finger 1 on two or more strings at the same fret is a barre, worked out the way
  the build script already does.
- Optionally, other names for the same chord (Gsus4add6 is often written G6sus4), so a search for
  either finds it.
- Optionally, a description to be spoken for a suffix unstrung does not know, such as "suspended
  4th, added 6th". Without one the suffix is spoken as written.

The notes come from the frets, so a new chord needs no interval formula to be played, spelled or
read out.

### Naming

Chord names in unstrung come from `identifyChordFromNotes`, with the library annotating where the
notes spell its name. A chord of your own keeps the name you give it. One possible Gsus4add6,
string 6 fret 3, string 5 not played, strings 4 and 3 open, string 2 fret 1, string 1 open,
sounds G, C, D and E, which the theory code names Cadd9 with G in the bass. The library should keep
Gsus4add6 and note that the same notes also spell Cadd9 over G, the way it already notes other
names. Your suffixes are not added to `IDENTIFY_SUFFIXES`, so Frets to Chord still names shapes
from theory; a shape of yours is matched by its frets and named as you named it.

## Proposed: the dialog

One dialog, titled New Chord, Add Fingering or Edit Fingering, in this order:

- **Chord name**, a combo box. It searches existing names and accepts a new one. Add Fingering
  fills it in.
- **Six string rows, 6 to 1**, each with the string control Frets to Chord already has and a
  Finger list. The Finger list is available only on a fretted string.
- **A status line** that updates as you change things: the notes sounded, and any problem with
  the fingering. Problems: one finger at two different frets with no barre, a fretted string with
  no finger, a stretch over four frets, and, for a name unstrung knows, notes that do not fit it.
- **Play, Save Chord and Cancel**, in the usual flex button row.

A one-line text field could come later, as the strokes field does for strumming patterns: frets
with the finger after a slash, string 6 first, such as `3/3 x 0 0 1/1 0`, read back in words in
the line after it. The six rows are enough for a first version.

### Where it opens from

- **Chord Library, Search Results:** an Add Fingering button under each chord. A chord with no
  fingering says so on that line. Your own fingerings also have Edit and Delete.
- **Chord Library, after the search field:** New Chord.
- **Frets to Chord:** Add to Chord Library, which opens the dialog with the six strings already
  set from Frets to Chord, leaving the fingers and the name. Likely the quickest way to define a
  chord.

## Recommendation: not to send these to chords-db

Checked 2026-11-01 with `gh`:

- Its last commit is 2025-10-14. Every pull request opened since February 2026 (#38, #40 to #43,
  #45 to #47) is still open or was closed without merging.
- unstrung uses chords-db only for shapes, re-checks every voicing and drops the ones that fail, so
  a fix there would reach unstrung only after a new chords-db release and a rebuild.
- chords-db files chords by key and suffix, so sus4add6 would be a new suffix there, not one new
  chord.

Your own chords stay personal. For fingerings that would help anyone, above all for the 38
unfingered chords: a small hand-written file of extra voicings in this repository, read by
`scripts/build-chord-library.mjs` and checked the same way as chords-db's, so they ship with the
next release. An error found in chords-db is worth an issue there, which costs little.

Since 2026-11-02 that file is `scripts/chord-library/voicings.json`, which holds every shipped shape,
not only the extra ones. See `chord-library-maintenance.md`.

## Proposed: your chords travel in .atex progressions

### What a saved progression holds already

`songToAlphaTex` in `src/shared/songScore.mjs` writes a `\chord` line for each chord, with its name
and frets from string 1 to string 6, `x` for a string not played:
`\chord ("Gsus4add6" 0 1 0 0 x 3)`. Each measure names its chord with `ch` on the beat it starts,
and the strummed notes carry the frets. So a received file has everything but the fingers.

What is missing is in reading. A name the library does not know stops the measure in `readBar`
("it names a chord unstrung does not know"), and the Open Saved Progression dialog lists the file
as one that cannot be opened, although its frets are in the file.

### Fingers go on the notes, with `lf`

alphaTab 1.8.4's `\chord` takes a name, one fret per string, and the properties `firstfret`,
`barre`, `showdiagram`, `showfingering` and `showname`. Its `Chord` model has no finger for a
string. A note can carry a left-hand finger with `lf`, kept in the model as `note.leftHandFinger`.

The first time a chord is strummed, its fretted notes carry their fingers:

```
(3.6{lf 4} 0.4 0.3 1.2{lf 2} 0.1).4{ch "Gsus4add6"}
```

alphaTex counts `lf` from the thumb: 1 thumb, 2 index, 3 middle, 4 ring, 5 little. So the writer
adds one to unstrung's finger numbers. alphaTab's `Fingers` values after loading are 0 thumb,
1 index, 2 middle, 3 ring, 4 little, the same as unstrung's, so the reader uses them as they are.
A note with no `lf` reads as -2, unknown.

Tested 2026-11-01 by loading text with `AlphaTexImporter` in Node, alphaTab 1.8.4:

- `\chord ("Gsus4add6" 0 1 0 0 x 3)` with the line above loaded. The chord read as strings
  `0,1,0,0,-1,3` from string 1, and the notes as string 6 fret 3 finger 3, string 2 fret 1
  finger 1, the open strings -2.
- A new property, `\chord ("Gsus4add6" 0 1 0 0 x 3) { fingers (0 1 0 0 x 3) }`, failed: alphaTab
  refuses the whole file for an unrecognized property. So fingers cannot go in `\chord`.
- A comment line, `// unstrung fingers Gsus4add6: 3/3 x 0 0 1/1 0`, was ignored without error.
  But comments are not in alphaTab's model, so anything that rewrites the file from the model
  loses them. `lf` on the notes is kept.

Programs built on alphaTab show the `lf` marks as fingering on the notes, and they survive a
conversion to Guitar Pro.

Only the first strike of each chord needs them; the writer regenerates the whole file on every
save, so they stay on whichever strike is first.

### Reading a file with chords you do not have

Before the measures are read, unstrung lists the file's `\chord` lines and sorts each against your
library:

- **New name:** not in your library. The name is split into root and suffix, Gsus4add6 into G and
  sus4add6. Where the split is ambiguous, as in Gb5, the root is the reading whose root the frets
  actually sound.
- **Known name, new shape:** you have the chord but not this fingering.
- **Known name and shape:** nothing to report.

The progression opens either way. A chord missing from your library is added to the index for
this file only, so it plays from the file's frets and fingers. Then a dialog lists what is
missing, one checkbox each, saying how it is played: "Gsus4add6: string 6 fret 3 ring finger,
string 5 not played, string 4 open, string 3 open, string 2 fret 1 index finger, string 1 open".
Buttons: Add Selected and Not Now. Not Now leaves the progression working as it is.

A chord with a name you already use but other notes, such as someone else's Gsus4add6 sounding
something other than G, C, D and E, is said so and offered as a separate chord, not as another
fingering of yours.

### Strumming patterns do this already

A progression using one of your strumming patterns writes the pattern into the notes, and a reader
without it keeps it as the progression's own (see `saved-progressions-design.md` and
`strumming-patterns-and-metronome.md`). The same dialog could offer to add that pattern to the
reader's patterns.

## Where it would go in the code

- `src/shared/`: the chord-of-your-own format, checking a fingering, merging into the library,
  splitting a name into root and suffix. No DOM or Node, so it works in the web version.
- `src/main/main.js`, `src/main/preload.js` and `src/web/platform.js`: save, export and import your
  chords, beside the strumming pattern equivalents (`saveStrummingPatterns`,
  `exportStrummingPatterns`, `importStrummingPatterns`).
- `src/shared/songScore.mjs`: `songToAlphaTex` writes `lf`; reading collects `\chord` lines and
  checks them before `readBar`; `progressionFromSong` accepts chords the file defines.
- `src/renderer/renderer.js` and `index.html`: the chord dialog, the buttons in the Chord Library
  and Frets to Chord, the missing-chords dialog.
- `scripts/build-chord-library.mjs`: the repository's own extra voicings, if wanted.
- `user-docs/features.md`: the Chord Library, Frets to Chord and Saving and Opening Progressions
  sections.
- Nothing needs Electron.
